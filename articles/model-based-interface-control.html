Interface Control Is a Modeling Problem

The ICD is a document describing something that isn't one.

Interfaces are where systems fail. Not usually inside a subsystem, subsystem teams know their own domain, test it thoroughly, and generally deliver something that works in isolation. Failures cluster at the boundaries, where two teams each built to their own reading of a shared agreement.

The artifact that's supposed to prevent this is the Interface Control Document. And the ICD has a structural problem: it is a document describing something that is not a document. An interface is a set of typed relationships between elements that exist elsewhere. Writing that down in prose creates a copy, and the copy immediately begins diverging from the thing it describes.

How ICDs go stale

The mechanism is mundane. A signal's range changes during detailed design. The change is captured in the subsystem's own documentation and in the code. Updating the ICD requires locating it, determining which of several tables mentions the signal, editing the entry, and routing the document for re-approval: a process measured in weeks, for a change that took an afternoon.

Under schedule pressure, this gets deferred. Not skipped: deferred, with genuine intent to catch up. Then it happens again. Within a few months the ICD describes an interface that no longer exists, and the teams on both sides know this, so they stop consulting it and coordinate directly by email instead. The document is still formally the controlling agreement. It is functionally abandoned, and its continued formal status is worse than nothing, because a new team joining the program will read it and believe it.

I want to be careful not to frame this as a discipline failure. The engineers deferring those updates are making a locally rational tradeoff given the cost of the update mechanism. The mechanism is the problem.

The other failure: modeling the organization instead of the system

There is a second reason interface definition fails, and it is more fundamental than staleness. Teams model their own organization rather than the system. The packages mirror the org chart, the boundaries fall where reporting lines fall, and the resulting structure describes who works on what instead of how the system is put together.

This looks reasonable, and it is how most programs partition work. But an interface between two subsystems is a property of the system, not of the two teams that happen to own them. When the decomposition follows the organization, every interface lands on a boundary owned by two groups or by nobody, and in practice it is nobody. The interface becomes the seam between two org units rather than a modeled element with a definition, a type, and an owner.

You can see the consequence in the artifacts. The ICD ends up describing a negotiation between departments rather than a connection between components, which is why so many of them read as agreements about responsibility instead of specifications of behavior. Reorganize the company and the model needs rework, which is a clear sign it was describing the wrong thing.

Partition by interface instead. Every interface gets one owning engineer responsible for defining it precisely enough that both sides can implement independently. Which org that engineer reports into matters far less than whether they exist at all.

What modeling the interface changes

If the interface is defined in the system model rather than described in a document, ports with types, connections between them, signals with units and ranges and update rates as structured attributes, several things become possible that prose cannot support.

Consistency becomes checkable. A signal produced with one unit and consumed as another is a query, not a careful reading. Type mismatches, range incompatibilities, a producer's update rate slower than its consumer's requirement, all detectable automatically, all common, all currently caught by humans comparing tables across documents, if caught at all.

Completeness becomes checkable. Every port connected. Every signal with exactly one producer. No consumer reading something nothing produces. These are cheap graph queries and they catch integration defects months before integration.

The document becomes a view. This is the part that matters organizationally. Programs need ICDs: for contracts, for suppliers, for certification. The mistake is treating the document as the source. Generate it from the model instead, and it can never be stale, because it's regenerated on demand from the current state. Engineers update the model, which they're doing anyway; the document follows for free.

Interfaces and cyber analysis

There's a second reason to model interfaces properly, and on connected platforms it has become the more urgent one.

Threat analysis on a networked system needs to answer questions about reachability. If an attacker compromises this component, what can they reach? Which paths cross a trust boundary? Which interfaces carry data that influences a safety-relevant function? These are graph traversals over the interface topology.

If the interface definition is a set of documents, these questions can only be answered by a human reading all of them and building a mental model, for a system with hundreds of components, this is not reliably possible, and the analysis is incomplete in ways nobody can quantify. If the topology is modeled, the same questions become queries you can re-run after every architectural change.

Model-based interface definition and cybersecurity threat analysis turn out to be the same underlying capability. Once the connection topology is machine-readable and typed, threat analysis is a set of traversals over it. Without that, security analysis on a large connected system is largely an exercise in expert intuition, and expert intuition does not scale to the interface counts on a modern vehicle or aircraft.

Realistic caveats

Two things are worth saying honestly. First, this only works if the model is actually maintained. Replacing a stale document with a stale model is not progress. What makes the model likelier to stay current is that engineers have other reasons to touch it, it feeds analysis, generates the document, drives the checks, whereas an ICD has exactly one use and that use is someone else's problem.

Second, not everything belongs in the model. Rationale, negotiated exceptions, historical context for a strange design choice, these are prose and should stay prose. The goal isn't to eliminate documents. It's to stop using documents as the storage format for structured, checkable, relational data, which is what a signal table is.

The transition

Nobody converts a program's interface definitions in one pass. What works is picking the boundary that hurts most, usually the one between two organizations that have had integration problems: modeling only that, generating its ICD from the model, and letting the result speak. When the generated document is demonstrably current and the neighboring hand-maintained ones demonstrably aren't, the argument makes itself.

It also inverts the usual adoption dynamic. Instead of asking teams to adopt modeling because it's the strategic direction, you're offering to take a maintenance burden off them. That's a much easier conversation, and in my experience it's the only version of it that produces durable adoption rather than compliance.
