Engineering Data Is a Graph

We store a relational structure as documents, then wonder why the questions are hard.

A requirement is satisfied by an architectural element. That element is realized by a part. The part is procured under a specification and verified by a test. The test was executed against a configuration, which was baselined at a milestone, which approved a set of changes, each of which modified some requirements.

That is a graph. Nodes are engineering objects; edges are typed, directional relationships. And on most programs it is stored as a set of documents, in different tools, with the edges recorded as text references that no machine can follow.

The consequence is that ordinary questions become expensive. Not exotic questions — ordinary ones. What is affected if this requirement changes? Which requirements are unverified? Which parts are involved in satisfying this safety requirement? Each is a traversal, and each currently requires an engineer to spend a day cross-referencing exports.

Why documents lose

A document can express a relationship — "this requirement is satisfied by the power distribution module" — but only as prose. To follow it, something must resolve the phrase to an object. A human does this using context. A machine cannot, reliably, because the same module appears as "PDM," "power distribution," "the PDU," and "P/N 4471-002" across four documents written by three teams.

This is why traceability matrices exist: they're an attempt to extract the graph from the documents into a form that can be queried. But a matrix is a flattened projection. It captures one relationship type between two object types, loses everything else, and goes stale the moment either side changes — the graph reconstituted badly, once, manually.

Typed edges are the whole point

A generic "related to" edge is nearly worthless. The value comes from types that carry meaning, because meaning is what makes a query answerable.

Satisfies means an element implements a requirement, which implies obligations: if the requirement changes, the element may no longer satisfy it. Derives from means a requirement was decomposed from a parent, which implies that the children must collectively be sufficient. Verifies means a test demonstrates satisfaction, which implies a currency question — was the test run against a version of the design that still resembles this one?

With those types, the query "which requirements have a satisfies edge but no verifies edge" is one line and answers the most important question in verification planning. Without them, it's a week of spreadsheet work and the answer is out of date on arrival.

Versioning is not optional

A graph of the current state answers questions about now. Most of the questions that matter are about change.

What changed since the last baseline. Which links became suspect as a result. Whether this test result is still valid given the design has moved. Which decisions were made under assumptions that no longer hold. None of these are answerable from a snapshot — they need history, and specifically they need the ability to compare two states of the graph and characterize the difference in engineering terms rather than as a textual diff.

That "in engineering terms" qualifier does a lot of work. Anyone can diff two exports. The useful statement isn't "these 340 lines differ" but "requirement PWR-114's allocation changed, which invalidates the satisfy link to the sensor module, which means test TC-2201 no longer verifies the current requirement" — a derived consequence, computed by propagating the change along typed edges and applying the rules those types imply.

Change propagation as reachability

Once you have typed edges and versions, impact analysis becomes a reachability problem. Start at the changed node, walk edges whose semantics imply dependency, mark what you reach as potentially affected.

The naïve version fails immediately: everything is transitively connected to everything, so a change to a top-level requirement marks the entire program as affected, which is true and useless. Making it useful requires the propagation rules to be type-aware and to attenuate. A change to a requirement's text propagates strongly to elements that satisfy it. A change to an element's internal structure may not propagate to the requirement at all. A change to a test propagates to the verification status of what it verifies, but not back into the design.

Getting these rules right is the substance of the problem. Too permissive and every change floods the program with false impact, and people stop reading the reports. Too restrictive and real impacts are missed, which is worse, because now there's a tool people trust that's wrong. I don't think there's a universal rule set — the tuning is domain-specific and it's earned through calibration against real change histories on a real program.

The ontology question

All of this presumes agreement on what the node and edge types are — which is an ontology, and ontology work has a reputation for consuming years and producing taxonomies nobody uses.

The reputation is partly earned, and the failure mode is recognizable: modeling the domain in full generality before anyone has tried to answer a question with it. What works better is starting from the queries. Pick the ten questions the program actually needs answered, determine the minimum type system that answers them, and extend only when a new question demands it. The ontology stays small, every type earns its existence, and the thing is useful from the first week rather than the third year.

What it buys

When it works, the shift is from questions that take days to questions that take seconds, which changes which questions get asked. Nobody runs an impact analysis that costs a week unless the change is large. If it costs a second, you run it on every change — and the small changes are precisely the ones whose consequences get missed.

That's the underlying argument for treating engineering data as what it structurally is. Not elegance. The cost of asking a question determines how often it's asked, and how often it's asked determines what the program knows about itself.
